# Findings — bugs surfaced while writing E2E tests

Potential defects discovered against `https://thinkrank.test` while building the
suite. Not yet filed. Repo routing: free → `WPDevelopers/thinkrank`, pro →
`WPDevelopers/thinkrank-pro`. (No AI attribution when filing.)

---

## 1. [Medium] URL Inspection `status` returns HTTP 403 for a non-authorization error

- **Repo:** thinkrank-pro
- **Where:** `includes/api/class-url-inspection-endpoint.php` — `get_status()` (~L344) and `batch_inspect()`
- **What:** When a scan halts on a site-level error (`state['site_error']`, e.g. Google
  Search Console reports *"You do not own this site…"*), `get_status()` returns the
  response with **HTTP 403**. The WP user *is* authorized (`check_permissions()` =
  `manage_options` passes) — this is an upstream Google condition, not an authorization
  failure. 403 misleads API clients, monitoring, and browser code into treating it as a
  permissions problem.
- **Repro:** `GET /wp-json/thinkrank-pro/v1/url-inspection/status` as admin after a scan
  halted on a site-error → `403` with body `{success:false, data:{…}, message:"You do not
  own this site…"}`.
- **Expected:** `200` (request succeeded; body already carries `success:false` + message),
  or a dependency/upstream code like `424`/`502`. Not `403`.
- **Severity:** Medium — wrong semantics; breaks clients that branch on status code.

## 2. [High] Physical `robots.txt` present but `/robots.txt` returns HTTP 404

- **Repo:** thinkrank (free) — robots.txt handling
- **Where:** `includes/frontend/class-seo-manager.php` `filter_robots_txt()` (hooks WP's
  *virtual* `robots_txt` filter) vs. a **physical** `robots.txt` written to the web root.
- **What:** A physical `robots.txt` exists in the WordPress root (ThinkRank-generated,
  `# Robots.txt generated by ThinkRank SEO`), but requesting `https://thinkrank.test/robots.txt`
  returns **HTTP 404**. WordPress only registers its virtual robots.txt rewrite when **no**
  physical file exists; with a physical file present, WP does not serve it and returns 404,
  while the plugin's `robots_txt` filter never runs either.
- **Impact:** Search engines treat a 404 robots.txt as *"no rules"* and ignore the
  directives entirely — the configured crawl rules (and the `Sitemap:` hint) are not applied.
- **Repro:** `curl -sSkI https://thinkrank.test/robots.txt` → `HTTP/2 404`, though the body
  contains ThinkRank robots content.
- **Expected:** `/robots.txt` serves the generated rules with **HTTP 200** (either don't
  write a physical file and rely on the virtual filter, or ensure the physical file is
  actually served).
- **Severity:** High — directly affects crawler behavior / SEO. Needs confirmation of
  whether the physical file is written by the plugin vs. a migration/import step.
- **Note:** Partly environment-dependent (nginx/Herd static handling) — confirm on a
  standard install before filing.
